# Lab 4：分片键值服务

## 实验目标

构建一个由多个 Raft 复制组组成的分片键值服务。每个复制组只负责部分键空间；Shard Master 记录每个 Shard 当前归属哪个复制组。客户端根据配置找到负责的组。系统需要支持复制组加入、离开和 Shard 重新分配，并在配置变化时迁移对应数据。

整个系统对客户端提供线性一致的 `Get`、`Put` 和 `Append` 操作。Lab 4 的 Shard Master 和 Sharded KV Server，以及 Lab 3 的 KV 服务，必须复用同一份 Raft 实现。

## Part 4A：Shard Master

- 实现一个由 Raft 复制的配置服务。
- 配置需要记录配置编号、每个 Shard 的归属组，以及各组的服务器列表。
- 支持复制组加入、离开、将指定 Shard 移至指定组，以及查询当前或历史配置。
- 每次配置变更应形成新的配置历史；历史查询需要返回对应版本，而不只是当前状态。
- 分配结果应满足实验要求的负载平衡和尽量减少 Shard 移动。
- 处理并发请求及客户端 RPC 重试造成的重复操作。

验收重点：Join、Leave、Move、历史 Query、并发变更、故障环境和 Shard 转移数量要求。

## Part 4B：Sharded Key/Value Server

- 实现多个 Raft 复制组，每组只服务当前配置分配给自己的 Shard。
- 客户端根据 key 找出 Shard，再查询配置并向负责该 Shard 的组发送操作。
- 配置改变后，将 Shard 的键值数据从旧组交接给新组。
- 迁移过程中需防止旧组和新组同时对同一 Shard 提供冲突服务，也不能丢失已确认的操作。
- 组加入或离开时，所有受影响的 Shard 最终都应由新配置指定的组负责。
- 配置变化不应破坏线性一致性；未受影响的 Shard 应按基础要求继续提供服务。
- 需要在不可靠网络和并发客户端请求中正确处理迁移、重试及重复操作。

验收重点：单组基础行为、多组加入/离开、Shard 数据迁移、服务器及网络故障、并发客户端操作和线性一致性。

## 可选挑战题

以下内容属于扩展挑战，基础 Part 4A/4B 完成后再考虑：

### Challenge 1：迁移后的状态回收

迁移完成后，旧复制组不应无限期保留已经不再负责的 Shard 状态。扩展要求是安全地清理这些过期状态，同时不能影响重试中的迁移或有效客户端操作。

### Challenge 2：配置变化期间的服务可用性

- 让正在变更配置的组继续服务不受本次迁移影响的 Shard。
- 进一步扩展时，某个目标组收到部分待迁移 Shard 后，可以尽早提供这些 Shard 的服务，而无需等待整次配置变化全部结束。

## 主要接口与约束

- 实验代码位于 `shardmaster` 和 `shardkv` 相关目录；以 2020 starter code 中的接口及测试为准。
- 复制组之间通过 RPC 交互，不应依赖共享进程状态。
- Shard 的分配配置、服务权限和数据迁移必须相互一致。
- 最终验收会复跑 Lab 2、Lab 3 和 Lab 4 测试；改动不能破坏前序实验。
